---
title: Upgrade to v0.2
description: Move to public SDK aliases, Nuxt 4.6 server APIs, and runtime gateway secrets.
---

## Framework and SDK versions

Use Nuxt 4.6 or newer in the supported Nuxt 4 range. Standalone Nitro 2 and Nitro 3 remain supported. The owned Files SDK is 2.6.2; no separate SDK installation is needed. Published Nuxt 5 prereleases and Vite server are experimental, with separate fixture coverage rather than a promise of future stable compatibility.

## Migrate existing imports

Replace application imports from `files-sdk` and `files-sdk/*` with `#files-sdk` and `#files-sdk/*`, then run `nuxt prepare`. Keep configuration helpers imported from `nuxt-files-sdk/config` and server utilities from `nuxt-files-sdk/runtime`.

```ts [files.config.ts]
import { defineFilesConfig } from 'nuxt-files-sdk/config'
import { versioning } from '#files-sdk/versioning'

export default defineFilesConfig({
    storage: {
        adapter: 'fs',
        config: { root: '.data/files' },
        plugins: [versioning()],
    },
})
```

Remove a direct `files-sdk` dependency if the application only uses it through this integration. A separate SDK installation can coexist; bare `files-sdk` imports keep resolving to that installation. The module owns its SDK version, and its aliases select that version for runtime code and generated types.

## Layers and standalone Nitro

Aliases expose only the SDK's public exports. A Layer can import shared configuration through its own aliases, but the module reads only the configured `files.config.ts`; it does not discover or merge Layer configurations automatically.

Standalone Nitro uses the same SDK aliases. Regenerate your project types and follow the generated tsconfig setup in [Nitro Module](/advanced/nitro-module). Nitro 2 and Nitro 3 remain supported without installing Nuxt.

## Additional dependencies and development updates

Keep any provider or plugin packages needed by your configuration. The module synchronizes the owned SDK's optional peer ranges and reports confirmed missing or incompatible dependencies. Dynamic settings and dependencies needed only for an unused operation remain quiet; **Dependency details** in the Files panel shows those conditions.

Configuration and dependency changes trigger reevaluation during development. An invalid authorization configuration causes generated gateways to refuse requests until it is repaired, including requests handled by an older development worker.

## Server initialization and authorization

Nuxt uses public server APIs and generated templates. Explicit imports from `nuxt-files-sdk/runtime` and server auto-imports share one registry initialization path. Nitro is retained for native hooks, aliases, externals, and provider compatibility; Nuxt no longer initializes Files through a Nitro startup plugin. Standalone Nitro keeps its native plugin lifecycle.

The synchronous `useServerFiles` API, native error identity, lazy provider construction, and user-before-Nitro hook order are preserved. Configuration/dependency checks give advice without installing packages or prompting.

Update authorization helpers that expect `H3Event` to accept the public `RequestEvent` from `@nuxt/schema`. Use `event.req`, `event.url`, `event.context`, and `event.res` instead of Node-specific request/response fields. Standalone Nitro adapts its event to this contract. The available Request signal is forwarded; Nuxt 4.6's native Nitro 2 signal does not provide client-disconnect cancellation.

## Gateway secrets and existing tokens

Gateway secrets are selected at runtime: route `secret`, then `FILES_API_SECRET`, then a purpose-derived Nuxt `appSecret`. Standalone Nitro requires an explicit route or environment secret. Keep the chosen environment/root secret consistent across processes and avoid source-code secret literals, which can enter server bundles.

Upload tokens issued with an older automatically generated key may need to be presigned again after this change. Tokens using an unchanged explicit key continue to follow the native Files SDK 2.6.2 validation rules. The module does not add an old-token bypass or relax native signature, scope, or expiry checks.

## Experimental builders and performance

Nuxt 5 coverage uses an actual distributed prerelease and tests real build, gateway HTTP, and development paths. Vite server coverage is limited to basic Files SSR; generated gateways fail preparation, and Files DevTools/Nitro hooks are unavailable. See [Installation](/getting-started/installation) for the capability summary.

Performance measurements depend on framework versions, lockfiles, transport, and cache state. Compare new equivalent baseline and changed runs; older measurements are historical. Mixed timing and size results do not establish a blanket speed improvement.
