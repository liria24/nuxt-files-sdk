Choose the adapter that matches the storage available in the deployed server runtime. Provider options and operation behavior belong to the [Files SDK provider reference](https://files-sdk.dev/docs/providers); this page covers what Nuxt adds around them.

## Configure the production provider

Keep secrets in the deployment environment and resolve them when the server client is first requested:

```ts [files.config.ts]
export default defineFilesConfig({
    storage: {
        adapter: 'r2',
        config: () => ({
            accountId: process.env.CLOUDFLARE_ACCOUNT_ID!,
            accessKeyId: process.env.CLOUDFLARE_ACCESS_KEY_ID!,
            secretAccessKey: process.env.CLOUDFLARE_SECRET_ACCESS_KEY!,
            bucket: process.env.R2_BUCKET!,
        }),
    },
})
```

The resolver must be synchronous and runs on the first call to `useServerFiles()` for that storage.

## Install provider dependencies

Some providers need an optional SDK in the application that uses them. Follow the provider page's install instructions and add that package to the deployed application, not to `nuxt-files-sdk` itself.

On Cloudflare Workers, `r2`, `minio`, and `rustfs` use fetch by default. Install the AWS SDK if you explicitly select its client.

## Check the runtime constraints

- `memory` is process-local and loses data on restart.
- `fs` needs a persistent, writable filesystem. Many serverless filesystems are ephemeral or read-only.
- Cloud providers need outbound network access and secrets configured in the deployment environment.
- A provider's runtime and package requirements remain authoritative in its [Files SDK documentation](https://files-sdk.dev/docs/providers).

Do not treat `devStorage` as a production fallback. Provider construction and file-operation failures are returned unchanged; they never switch storage automatically.
